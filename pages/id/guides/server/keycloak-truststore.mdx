# Mengonfigurasi sertifikat terpercaya

Ketika NQRust-Identity berkomunikasi dengan layanan eksternal atau memiliki koneksi masuk melalui TLS, sistem harus memvalidasi sertifikat jarak jauh untuk memastikan bahwa sistem tersebut terhubung ke server yang terpercaya. Hal ini diperlukan untuk mencegah serangan man-in-the-middle.

Sertifikat dari klien atau server ini, atau CA yang menandatangani sertifikat ini, harus ditempatkan di dalam truststore. Truststore ini kemudian dikonfigurasi untuk digunakan oleh NQRust-Identity.

## [](#_mengonfigurasi_truststore_sistem)Mengonfigurasi Truststore Sistem

Sertifikat default truststore Java yang ada akan selalu terpercaya. Jika Anda memerlukan sertifikat tambahan, yang biasanya terjadi jika Anda memiliki sertifikat self-signed atau otoritas sertifikat internal yang tidak dikenali oleh JRE, sertifikat tersebut dapat diikutsertakan dalam direktori `conf/truststores` atau subdirektori. Sertifikat ini bisa berupa file PEM atau file PKCS12 dengan ekstensi `.p12`, `.pfx`, atau `.pkcs12`. Jika dalam format PKCS12, sertifikat harus tidak terenkripsi - yang berarti tidak diharapkan ada kata sandi.

Jika Anda memerlukan path alternatif, gunakan opsi `--truststore-paths` untuk menentukan file atau direktori tambahan di mana file PEM atau PKCS12 terletak. Path dihitung relatif terhadap tempat Anda menjalankan NQRust-Identity, jadi sangat disarankan untuk menggunakan path absolut. Jika direktori ditentukan, sistem akan secara rekursif mencari file truststore.

Setelah semua sertifikat yang relevan diikutsertakan, truststore akan digunakan sebagai truststore default sistem melalui properti `javax.net.ssl`, dan sebagai default untuk penggunaan internal dalam NQRust-Identity.

Contohnya:

```bash
bin/kc.[sh|bat] start --truststore-paths=/opt/truststore/myTrustStore.pfx,/opt/other-truststore/myOtherTrustStore.pem
```

Masih mungkin untuk secara langsung mengatur properti truststore Sistem `javax.net.ssl` Anda sendiri, tetapi lebih disarankan untuk menggunakan `--truststore-paths` sebagai gantinya.

## [](#_kebijakan_verifikasi_nama_host)Kebijakan Verifikasi Nama Host

Anda dapat memperhalus bagaimana nama host diverifikasi oleh koneksi TLS dengan properti `tls-hostname-verifier`.

*   `DEFAULT` (default) memungkinkan wildcard dalam nama subdomain (misalnya \*.foo.com) untuk mencocokkan nama dengan jumlah tingkatan yang sama (misalnya a.foo.com, tetapi bukan a.b.foo.com) - dengan aturan dan pengecualian untuk akhiran publik berdasarkan [https://publicsuffix.org/list/](https://publicsuffix.org/list/)
    
*   `ANY` berarti bahwa nama host tidak diverifikasi - mode ini sebaiknya tidak digunakan dalam produksi.
    
*   `WILDCARD` (usang) memungkinkan wildcard dalam nama subdomain (misalnya \*.foo.com) untuk mencocokkan apa saja, termasuk beberapa tingkatan (misalnya a.b.foo.com). Gunakan DEFAULT sebagai gantinya.
    
*   `STRICT` (usang) memungkinkan wildcard dalam nama subdomain (misalnya \*.foo.com) untuk mencocokkan nama dengan jumlah tingkatan yang sama (misalnya a.foo.com, tetapi bukan a.b.foo.com) - dengan beberapa pengecualian terbatas. Gunakan DEFAULT sebagai gantinya.
    
    Harap dicatat bahwa pengaturan ini tidak berlaku untuk koneksi LDAP yang aman, yang memerlukan pemeriksaan nama host yang ketat.
