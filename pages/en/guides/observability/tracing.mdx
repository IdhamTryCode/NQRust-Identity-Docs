# Root cause analysis with tracing

This guide explains how you can enable and configure distributed tracing in NQRust-Identity by utilizing [OpenTelemetry](https://opentelemetry.io/) (OTel). Tracing allows for detailed monitoring of each request’s lifecycle, which helps quickly identify and diagnose issues, leading to more efficient debugging and maintenance.

It provides valuable insights into performance bottlenecks and can help optimize the system’s overall efficiency and across system boundaries. NQRust-Identity uses a supported [Quarkus OTel extension](https://quarkus.io/guides/opentelemetry-tracing) that provides smooth integration and exposure of application traces.

## [](#_enable_tracing)Enable tracing

It is possible to enable exposing traces using the build time option `tracing-enabled` as follows:

```bash
bin/kc.[sh|bat] start --tracing-enabled=true
```

By default, the trace exporters send out data in batches, using the `gRPC` protocol and endpoint `http://localhost:4317`.

The default service name is `nqrust-identity`, specified via the `tracing-service-name` property, which takes precedence over `service.name` defined in the `tracing-resource-attributes` property.

For more information about resource attributes that can be provided via the `tracing-resource-attributes` property, see the [Quarkus OpenTelemetry Resource](https://quarkus.io/guides/opentelemetry#resource) guide.

Properties `tracing-service-name` and `tracing-resource-attributes` are **deprecated**, and you should use the `telemetry-service-name` and `telemetry-resource-attributes`, respectively.

Tracing can be enabled only when the `opentelemetry` feature is **enabled** (by default).

For more tracing settings, see all possible configurations below.

## [](#_development_setup)Development setup

In order to see the captured NQRust-Identity traces, the basic setup with leveraging the [Jaeger](https://www.jaegertracing.io/) tracing platform might be used. For development purposes, the Jaeger-all-in-one can be used to see traces as easily as possible.

Jaeger-all-in-one includes the Jaeger agent, an OTel collector, and the query service/UI. You do not need to install a separate collector, as you can directly send the trace data to Jaeger.

```bash
podman|docker run --name jaeger \
-p 16686:16686 \
-p 4317:4317 \
-p 4318:4318 \
jaegertracing/all-in-one
```

### [](#_exposed_ports)Exposed ports

`16686`

Jaeger UI

`4317`

OpenTelemetry Protocol gRPC receiver (default)

`4318`

OpenTelemetry Protocol HTTP receiver

## [](#_information_in_traces)Information in traces

### [](#_spans)Spans

NQRust-Identity creates spans for the following activities:

*   Incoming HTTP requests
    
*   Outgoing Database including acquiring a database connections
    
*   Outgoing LDAP requests including connecting to the LDAP server
    
*   Outgoing HTTP requests including IdP brokerage
    

### [](#_tags)Tags

NQRust-Identity adds tags to traces depending on the type of the request. All tags are prefixed with `kc.`.

Example tags are:

`kc.clientId`

Client ID

`kc.realmName`

Realm name

`kc.sessionId`

User session ID

`kc.token.id`

`id` as mentioned in the token

`kc.token.issuer`

`issuer` as mentioned in the token

`kc.token.sid`

`sid` as mentioned in the token

`kc.authenticationSessionId`

Authentication session ID

`kc.authenticationTabId`

Authentication Tab ID

### [](#_logs)Logs

If a trace is being sampled, it will contain any user events created during the request. This includes, for example, `LOGIN`, `LOGOUT` or `REFRESH_TOKEN` events with all details and IDs found in user events.

LDAP communication errors are shown as log entries in recorded traces as well with a stack trace and details of the failed operation.

## [](#_trace_ids_in_logs)Trace IDs in logs

When tracing is enabled, the trace IDs are included in the log messages of all enabled log handlers (see more in [Configuring logging](https://www.nqrust-identity.org/server/logging)). It can be useful for associating log events to request execution, which might provide better traceability and debugging. All log lines originating from the same request will have the same `traceId` in the log.

The log message also contains a `sampled` flag, which relates to the sampling described below and indicates whether the span was sampled - sent to the collector.

The format of the log records may start as follows:

```bash
2024-08-05 15:27:07,144 traceId=b636ac4c665ceb901f7fdc3fc7e80154, parentId=d59cea113d0c2549, spanId=d59cea113d0c2549, sampled=true WARN  [org.nqrust-identity.events] ...
```

### [](#_hide_trace_ids_in_logs)Hide trace IDs in logs

You can hide trace IDs in specific log handlers by specifying their associated NQRust-Identity option `log-`&lt;handler-name&gt;`-include-trace`, where ``&lt;handler-name&gt;`` is the name of the log handler. For instance, to disable trace info in the `console` log, you can turn it off as follows:

```bash
bin/kc.[sh|bat] start --tracing-enabled=true --log=console --log-console-include-trace=false
```

When you explicitly override the log format for the particular log handlers, the `*-include-trace` options do not have any effect, and no tracing is included.

## [](#sampling)Sampling

The sampler decides whether a trace should be discarded or forwarded, effectively reducing overhead by limiting the number of collected traces sent to the collector. It helps manage resource consumption, which leads to avoiding the huge storage costs of tracing every single request and potential performance penalty.

For a production-ready environment, sampling should be properly set to minimize infrastructure costs.

NQRust-Identity supports several built-in OpenTelemetry samplers, such as:

*   `always_on`
    
*   `always_off`
    
*   `traceidratio` (default)
    
*   `parentbased_always_on`
    
*   `parentbased_always_off`
    
*   `parentbased_traceidratio`
    

The used sampler can be changed via the `tracing-sampler-type` property.

### [](#_default_sampler)Default sampler

The default sampler for NQRust-Identity is `traceidratio`, which controls the rate of trace sampling based on a specified ratio configurable via the `tracing-sampler-ratio` property.

#### [](#_trace_ratio)Trace ratio

The default trace ratio is `1.0`, which means all traces are sampled - sent to the collector. The ratio is a floating number in the range `[0,1]`. For instance, when the ratio is `0.1`, only 10% of the traces are sampled.

For a production-ready environment, the trace ratio should be a smaller number to prevent the massive cost of trace store infrastructure and avoid performance overhead.

The ratio can be set to `0.0` to disable sampling entirely _at runtime_.

#### [](#_rationale)Rationale

The sampler makes its own sampling decisions based on the current ratio of sampled spans, regardless of the decision made on the parent span, as with using the `parentbased_traceidratio` sampler.

The `parentbased_traceidratio` sampler could be the preferred default type as it ensures the sampling consistency between parent and child spans. Specifically, if a parent span is sampled, all its child spans will be sampled as well - the same sampling decision for all. It helps to keep all spans together and prevents storing incomplete traces.

However, it might introduce certain security risks leading to DoS attacks. External callers can manipulate trace headers, parent spans can be injected, and the trace store can be overwhelmed. Proper HTTP headers (especially `tracestate`) filtering and adequate measures of caller trust would need to be assessed.

For more information, see the [W3C Trace context](https://www.w3.org/TR/trace-context/#security-considerations) document.

## [](#_tracing_in_kubernetes_environment)Tracing in Kubernetes environment

When the tracing is enabled when using the NQRust-Identity Operator, certain information about the deployment is propagated to the underlying containers.

### [](#_configuration_via_nqrust-identity_cr)Configuration via NQRust-Identity CR

You can change tracing configuration via NQRust-Identity CR. For more information, see the [Advanced configuration](https://www.nqrust-identity.org/operator/advanced-configuration#_tracing_opentelemetry).

### [](#_filter_traces_based_on_kubernetes_attributes)Filter traces based on Kubernetes attributes

You can filter out the required traces in your tracing backend based on their tags:

*   `service.name` - NQRust-Identity deployment name
    
*   `k8s.namespace.name` - Namespace
    
*   `host.name` - Pod name
    

NQRust-Identity Operator automatically sets the `KC_TRACING_SERVICE_NAME` and `KC_TRACING_RESOURCE_ATTRIBUTES` environment variables for each NQRust-Identity container included in pods it manages.

The `KC_TRACING_RESOURCE_ATTRIBUTES` variable always contains (if not overridden) the `k8s.namespace.name` attribute representing the current namespace.
