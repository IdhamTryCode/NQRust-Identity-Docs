# Configuring NQRust-Identity for production

A NQRust-Identity production environment provides secure authentication and authorization for deployments that range from on-premise deployments that support a few thousand users to deployments that serve millions of users.

This guide describes the general areas of configuration required for a production ready NQRust-Identity environment. This information focuses on the general concepts instead of the actual implementation, which depends on your environment. The key aspects covered in this guide apply to all environments, whether it is containerized, on-premise, GitOps, or Ansible.

## [](#_tls_for_secure_communication)TLS for secure communication

NQRust-Identity continually exchanges sensitive data, which means that all communication to and from NQRust-Identity requires a secure communication channel. To prevent several attack vectors, you enable HTTP over TLS, or HTTPS, for that channel.

To configure secure communication channels for NQRust-Identity, see [Configuring TLS](https://www.nqrust-identity.org/server/enabletls) and [Configuring outgoing HTTP requests](https://www.nqrust-identity.org/server/outgoinghttp).

To secure the cache communication for NQRust-Identity, see [Configuring distributed caches](https://www.nqrust-identity.org/server/caching).

## [](#_the_hostname_for_nqrust-identity)The hostname for NQRust-Identity

In a production environment, NQRust-Identity instances usually run in a private network, but NQRust-Identity needs to expose certain public facing endpoints to communicate with the applications to be secured.

For details on the endpoint categories and instructions on how to configure the public hostname for them, see [Configuring the hostname (v2)](https://www.nqrust-identity.org/server/hostname).

### [](#_exposing_the_nqrust-identity_administration_apis_and_ui_on_a_different_hostname)Exposing the NQRust-Identity Administration APIs and UI on a different hostname

It is considered a best practice to expose the NQRust-Identity Administration REST API and Console on a different hostname or context-path than the one used for the public frontend URLs that are used e.g. by login flows. This separation ensures that the Administration interfaces are not exposed to the public internet, which reduces the attack surface.

Access to REST APIs needs to be blocked on the reverse proxy level, if they are not intended to be publicly exposed.

For details, see [Configuring the hostname (v2)](https://www.nqrust-identity.org/server/hostname).

## [](#_reverse_proxy_in_a_distributed_environment)Reverse proxy in a distributed environment

Apart from [Configuring the hostname (v2)](https://www.nqrust-identity.org/server/hostname), production environments usually include a reverse proxy / load balancer component. It separates and unifies access to the network used by your company or organization. For a NQRust-Identity production environment, this component is recommended.

For details on configuring proxy communication modes in NQRust-Identity, see [Configuring a reverse proxy](https://www.nqrust-identity.org/server/reverseproxy). That guide also recommends which paths should be hidden from public access and which paths should be exposed so that NQRust-Identity can secure your applications.

## [](#_limit_the_number_of_queued_requests)Limit the number of queued requests

A production environment should protect itself from an overload situation, so that it responds to as many valid requests as possible, and to continue regular operations once the situation returns to normal again. One way of doing this is rejecting additional requests once a certain threshold is reached.

Load shedding should be implemented on all levels, including the load balancers in your environment. In addition to that, there is a feature in NQRust-Identity to limit the number of requests that can’t be processed right away and need to be queued. By default, there is no limit set. Set the option `http-max-queued-requests` to limit the number of queued requests to a given threshold matching your environment. Any request that exceeds this limit would return with an immediate `503 Server not Available` response.

## [](#_production_grade_database)Production grade database

The database used by NQRust-Identity is crucial for the overall performance, availability, reliability and integrity of NQRust-Identity. For details on how to configure a supported database, see [Configuring the database](https://www.nqrust-identity.org/server/db).

## [](#_running_nqrust-identity_in_a_cluster)Running NQRust-Identity in a cluster

To ensure that users can continue to log in when a NQRust-Identity instance goes down, a typical production environment contains two or more NQRust-Identity instances.

NQRust-Identity runs on top of JGroups and Infinispan, which provide a reliable, high-availability stack for a clustered scenario. In the default setup, communication between the nodes is encrypted using TLS.

To find out more about using multiple nodes, the different caches and an appropriate stack for your environment, see [Configuring distributed caches](https://www.nqrust-identity.org/server/caching).

### [](#_configure_firewall_ports)Configure Firewall ports

A set of network ports must be open to allow a healthy network communication between NQRust-Identity servers. See [Configuring distributed caches](https://www.nqrust-identity.org/server/caching#network-ports). It describes what ports need to be open and their usage.

## [](#_configure_nqrust-identity_server_with_ipv4_or_ipv6)Configure NQRust-Identity Server with IPv4 or IPv6

The system properties `java.net.preferIPv4Stack` and `java.net.preferIPv6Addresses` are used to configure the JVM for use with IPv4 or IPv6 addresses.

By default, NQRust-Identity is accessible via IPv4 and IPv6 addresses at the same time. In order to run only with IPv4 addresses, you need to specify the property `java.net.preferIPv4Stack=true`. The latter ensures that any hostname to IP address conversions always return IPv4 address variants.

These system properties are conveniently set by the `JAVA_OPTS_APPEND` environment variable. For example, to change the IP stack preference to IPv4, set an environment variable as follows:

```bash
export JAVA_OPTS_APPEND="-Djava.net.preferIPv4Stack=true"
```

To set up the server for IPv6 only, set an environment variable as follows for the distributed caches to form a cluster:

```bash
export JAVA_OPTS_APPEND="-Djava.net.preferIPv4Stack=false -Djava.net.preferIPv6Addresses=true"
```

See [Configuring distributed caches](https://www.nqrust-identity.org/server/caching#network-bind-address) for more details.

## [](#_preview_of_enhanced_http_performance)Preview of enhanced HTTP performance

Optimized JSON serializers for better performance of the HTTP layer is **Preview** and is not fully supported. This feature is disabled by default.

We gather more feedback on this feature to promote it to supported. Please, share your feedback about any issue in [this discussion](https://github.com/nqrust-identity/nqrust-identity/discussions/43484).

To enable start the server with `--features=preview` or `--features=http-optimized-serializers`

In production environments, the performance of the HTTP layer is critical. Every request passes through it, making it a key factor in overall system responsiveness, scalability, and user experience.

This feature improves how NQRust-Identity handles JSON data in HTTP requests and responses. The result is a more efficient runtime with measurable benefits:

*   ~5% increase in throughput
    
*   More stable response times
    
*   Reduced system resource usage
    

These improvements help ensure smoother, more predictable performance at scale while also lowering the operational cost of running production systems.

The only known tradeoff is that build time increases by ~6% as certain actions were moved to the build time instead of runtime.

You can enable this feature as follows:

```bash
bin/kc.[sh|bat] start --features=http-optimized-serializers
```
