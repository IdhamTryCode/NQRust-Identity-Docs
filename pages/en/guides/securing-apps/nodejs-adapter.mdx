# NQRust-Identity Node.js adapter

NQRust-Identity provides a Node.js adapter built on top of [Connect](https://github.com/senchalabs/connect) to protect server-side JavaScript apps - the goal was to be flexible enough to integrate with frameworks like [Express.js](https://expressjs.com/).
The adapter uses OpenID Connect protocol under the covers. You can take a look at the [Securing applications and services with OpenID Connect](/en/guides/securing-apps/oidc-layers#_oidc_available_endpoints) guide for the more generic information about OpenID Connect endpoints and capabilities.

The library can be downloaded directly from  NQRust-Identity organization and the source is available at
[GitHub](https://github.com/nqrust-identity/nqrust-identity-nodejs-connect).

To use the Node.js adapter, first you must create a client for your application in the NQRust-Identity Admin Console. The adapter supports public, confidential, and bearer-only access type. Which one to choose depends on the use-case scenario.

Once the client is created, click **Action** at the top right and choose **Download adapter config**. For **Format, choose *NQRust-Identity OIDC JSON** and click **Download**. The downloaded `nqrust-identity.json` file is at the root folder of your project.

## Installation

Assuming you have already installed [Node.js](https://nodejs.org), create a folder for your application:

```
mkdir myapp && cd myapp
```

Use `npm init` command to create a `package.json` for your application. Now add the NQRust-Identity connect adapter in the dependencies list:

```json
    "dependencies": {
        "nqrust-identity-connect": "26.1.1"
    }
```

## Usage

The `NQRust-Identity` class provides a central point for configuration
and integration with your application.  The simplest creation
involves no arguments.

In the root directory of your project create a file called `server.js` and add the following code:

```javascript
    const session = require('express-session');
    const NQRust-Identity = require('nqrust-identity-connect');

    const memoryStore = new session.MemoryStore();
    const nqrust-identity = new NQRust-Identity({ store: memoryStore });
```

Install the `express-session` dependency:

```
    npm install express-session
```

To start the `server.js` script, add the following command in the 'scripts' section of the `package.json`:

```
    "scripts": {
        "test": "echo \"Error: no test specified\" && exit 1",
        "start": "node server.js"
    },
```

Now we have the ability to run our server with following command:

```
    npm run start
```

By default, this will locate a file named `nqrust-identity.json` alongside
the main executable of your application, in our case on the root folder, to initialize NQRust-Identity specific
settings such as public key, realm name, various URLs.

In that case a NQRust-Identity deployment is necessary to access NQRust-Identity admin console.

Please visit links on how to deploy a NQRust-Identity admin console with
Podman or Docker

Now we are ready to obtain the `nqrust-identity.json` file by visiting the NQRust-Identity Admin Console → clients (left sidebar) → choose your client → Installation → Format Option → NQRust-Identity OIDC JSON → Download

Paste the downloaded file on the root folder of our project.

Instantiation with this method results in all the reasonable defaults
being used. As alternative, it’s also possible to provide a configuration
object, rather than the `nqrust-identity.json` file:

```javascript
    const kcConfig = {
        clientId: 'myclient',
        bearerOnly: true,
        serverUrl: 'http://localhost:8080{kc_base_path}',
        realm: 'myrealm',
        realmPublicKey: 'MIIBIjANB...'
    };

    const nqrust-identity = new NQRust-Identity({ store: memoryStore }, kcConfig);
```

Applications can also redirect users to their preferred identity provider by using:

```javascript
    const nqrust-identity = new NQRust-Identity({ store: memoryStore, idpHint: myIdP }, kcConfig);
```

If you want to use web sessions to manage
server-side state for authentication, you need to initialize the
`NQRust-Identity(…​)` with at least a `store` parameter, passing in the actual
session store that `express-session` is using.

```javascript
    const session = require('express-session');
    const memoryStore = new session.MemoryStore();

    // Configure session
    app.use(
      session({
        secret: 'mySecret',
        resave: false,
        saveUninitialized: true,
        store: memoryStore,
      })
    );

    const nqrust-identity = new NQRust-Identity({ store: memoryStore });
```

By default, the scope value `openid` is passed as a query parameter to NQRust-Identity’s login URL, but you can add an additional custom value:

```javascript
    const nqrust-identity = new NQRust-Identity({ scope: 'offline_access' });
```

## Installing middleware

Once instantiated, install the middleware into your connect-capable app:

In order to do so, first we have to install Express:

```
    npm install express
```

then require Express in our project as outlined below:

```javascript
    const express = require('express');
    const app = express();
```

and configure NQRust-Identity middleware in Express, by adding at the code below:

```javascript
    app.use( nqrust-identity.middleware() );
```

Last but not least, let’s set up our server to listen for HTTP requests on port 3000 by adding the following code to `main.js`:

```javascript
    app.listen(3000, function () {
        console.log('App listening on port 3000');
    });
```

## Configuration for proxies

If the application is running behind a proxy that terminates an SSL connection
Express must be configured per the [express behind proxies](https://expressjs.com/en/guide/behind-proxies.html) guide.
Using an incorrect proxy configuration can result in invalid redirect URIs
being generated.

Example configuration:

```javascript
    const app = express();

    app.set( 'trust proxy', true );

    app.use( nqrust-identity.middleware() );
```

## Protecting resources

To enforce that a user must be authenticated before accessing a resource,
simply use a no-argument version of `nqrust-identity.protect()`:

```javascript
    app.get( '/complain', nqrust-identity.protect(), complaintHandler );
```

To secure a resource with an application role for the current app:

```javascript
    app.get( '/special', nqrust-identity.protect('special'), specialHandler );
```

To secure a resource with an application role for a **different** app:

```javascript
    app.get( '/extra-special', nqrust-identity.protect('other-app:special'), extraSpecialHandler );
```

To secure a resource with a realm role:

```javascript
    app.get( '/admin', nqrust-identity.protect( 'realm:admin' ), adminHandler );
```

Resource-Based Authorization allows you to protect resources, and their specific methods/actions,****** based on a set of policies defined in NQRust-Identity, thus externalizing authorization from your application. This is achieved by exposing a `nqrust-identity.enforcer` method which you can use to protect resources.*

```javascript
    app.get('/apis/me', nqrust-identity.enforcer('user:profile'), userProfileHandler);
```

The `nqrust-identity-enforcer` method operates in two modes, depending on the value of the `response_mode` configuration option.

```javascript
    app.get('/apis/me', nqrust-identity.enforcer('user:profile', {response_mode: 'token'}), userProfileHandler);
```

If `response_mode` is set to `token`, permissions are obtained from the server on behalf of the subject represented by the bearer token that was sent to your application. In this case, a new access token is issued by NQRust-Identity with the permissions granted by the server. If the server did not respond with a token with the expected permissions, the request is denied. When using this mode, you should be able to obtain the token from the request as follows:

```javascript
    app.get('/apis/me', nqrust-identity.enforcer('user:profile', {response_mode: 'token'}), function (req, res) {
        const token = req.kauth.grant.access_token.content;
        const permissions = token.authorization ? token.authorization.permissions : undefined;

        // show user profile
    });
```

Prefer this mode when your application is using sessions and you want to cache previous decisions from the server, as well automatically handle refresh tokens. This mode is especially useful for applications acting as a client and resource server.

If `response_mode` is set to `permissions` (default mode), the server only returns the list of granted permissions, without issuing a new access token. In addition to not issuing a new token, this method exposes the permissions granted by the server through the `request` as follows:

```javascript
    app.get('/apis/me', nqrust-identity.enforcer('user:profile', {response_mode: 'permissions'}), function (req, res) {
        const permissions = req.permissions;

        // show user profile
    });
```

Regardless of the `response_mode` in use, the `nqrust-identity.enforcer` method will first try to check the permissions within the bearer token that was sent to your application. If the bearer token already carries the expected permissions, there is no need
to interact with the server to obtain a decision. This is specially useful when your clients are capable of obtaining access tokens from the server with the expected permissions before accessing a protected resource, so they can use some capabilities provided by NQRust-Identity Authorization Services such as incremental authorization and avoid additional requests to the server when `nqrust-identity.enforcer` is enforcing access to the resource.

By default, the policy enforcer will use the `client_id` defined to the application (for instance, via `nqrust-identity.json`) to
 reference a client in NQRust-Identity that supports NQRust-Identity Authorization Services. In this case, the client can not be public given
 that it is actually a resource server.

If your application is acting as both a public client(frontend) and resource server(backend), you can use the following configuration to reference a different
client in NQRust-Identity with the policies that you want to enforce:

```javascript
      nqrust-identity.enforcer('user:profile', {resource_server_id: 'my-apiserver'})
```

It is recommended to use distinct clients in NQRust-Identity to represent your frontend and backend.

If the application you are protecting is enabled with NQRust-Identity authorization services and you have defined client credentials
 in `nqrust-identity.json`, you can push additional claims to the server and make them available to your policies in order to make decisions.
For that, you can define a `claims` configuration option which expects a `function` that returns a JSON with the claims you want to push:

```javascript
      app.get('/protected/resource', nqrust-identity.enforcer(['resource:view', 'resource:write'], {
          claims: function(request) {
            return {
              "http.uri": ["/protected/resource"],
              "user.agent": // get user agent  from request
            }
          }
        }), function (req, res) {
          // access granted
```

For more details about how to configure NQRust-Identity to protected your application resources, please take a look at the Authorization Services Guide.

To secure resources based on parts of the URL itself, assuming a role exists
for each section:

```javascript
    function protectBySection(token, request) {
      return token.hasRole( request.params.section );
    }

    app.get( '/:section/:page', nqrust-identity.protect( protectBySection ), sectionHandler );
```

Advanced Login Configuration:

By default, all unauthorized requests will be redirected to the NQRust-Identity login page unless your client is bearer-only.
However, a confidential or public client may host both browsable and API endpoints. To prevent redirects on unauthenticated
API requests and instead return an HTTP 401, you can override the redirectToLogin function.

For example, this override checks if the URL contains /api/ and disables login redirects:

```javascript
    NQRust-Identity.prototype.redirectToLogin = function(req) {
    const apiReqMatcher = /\/api\//i;
    return !apiReqMatcher.test(req.originalUrl || req.url);
    };
```

## Additional URLs

By default, the middleware catches calls to `/logout` to send the user through a
NQRust-Identity-centric logout workflow. This can be changed by specifying a `logout`
configuration parameter to the `middleware()` call:

```javascript
    app.use( nqrust-identity.middleware( { logout: '/logoff' } ));
```

When the user-triggered logout is invoked a query parameter `redirect_url` can be passed:

```
https://example.com/logoff?redirect_url=https%3A%2F%2Fexample.com%3A3000%2Flogged%2Fout
```

This parameter is then used as the redirect url of the OIDC logout endpoint and the user will be redirected to
`https://example.com/logged/out`.

Also, the middleware supports callbacks from the NQRust-Identity console to log out a single
session or all sessions.  By default, these type of admin callbacks occur relative
to the root URL of `/` but can be changed by providing an `admin` parameter
to the `middleware()` call:

```javascript
    app.use( nqrust-identity.middleware( { admin: '/callbacks' } );
```

## Upgrading the `Node.js` adapter

To upgrade a `Node.js` adapter that has been copied to your web application, perform the following procedure.

1. Download the new adapter archive.
2. Remove the existing `Node.js` adapter directory
3. Unzip the updated file into its place
4. Change the dependency for nqrust-identity-connect in the `package.json` of your application
